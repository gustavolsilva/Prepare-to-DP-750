🌐 Visão Unificada Completa: Integração Arquitetural de Ponta a Ponta

Implemente governança estrita de custos e recursos através de Cluster Policies JSON, Databricks Pools para inicialização rápida e Serverless SQL Warehouses de alta concorrência. Esta lição articula a ponte entre os fundamentos conceituais, a prática de engenharia no Azure Databricks e os critérios rigorosos de aprovação no exame Microsoft DP-750.

No dia a dia prático: No Azure Databricks, administradores utilizam Cluster Policies (definidas em JSON) para padronizar configurações de hardware, impor tags de centros de custo (`custom_tags`), limitar o número máximo de nós de workers e fixar o `autotermination_minutes`. Databricks Pools mantêm um conjunto de instâncias de máquinas virtuais Azure pré-inicializadas e ociosas (idle), reduzindo o tempo de inicialização de novos clusters de minutos para segundos. Para workloads de BI e consultas analíticas SQL, os Serverless SQL Warehouses fornecem elasticidade instantânea, cache inteligente e desligamento automático em até 1 minuto.

Diretriz oficial DP-750 & Decisão Arquitetural: No exame DP-750: Cluster Policies são a ferramenta primária para resolver conflitos entre flexibilidade para desenvolvedores e controle orçamentário de FinOps. Por exemplo, pode-se atribuir permissão `CAN_USE` na política 'Personal Compute' para cientistas de dados, enquanto engenheiros de produção usam a política 'Shared Compute'. Em SQL Warehouses, o scaling policy 'Serverless' ajusta clusters adicionais automaticamente quando a fila de queries cresce, garantindo SLA sem intervenção manual.

Mecânica Interna & Governança Executiva: Internals de Cluster Policies: Utilizam operadores JSON como `fixed`, `allowlist`, `blocklist`, `regex`, `range` e `defaultValue`. Por exemplo, a regra `"spark_version": {"type": "fixed", "value": "auto:latest-lts"}` força o uso automático da versão Long-Term Support mais recente, prevenindo que equipes utilizem runtimes legados ou não homologados com vulnerabilidades de segurança. Em termos de FinOps corporativo: Impacto no TCO: SQL Warehouses tradicionais exigiam espera de 5 minutos para autostart e tinham tempo mínimo de autostop de 10-15 minutos. Com Serverless SQL Warehouses, o startup leva 5 segundos e o autostop pode ser reduzido para 1 minuto, economizando até 70% do custo de computação ociosa em equipes de Analytics.

Hands-on Lab Walkthrough

Lab 0005: Governança de FinOps: Cluster Policies e Serverless SQL Warehouses

⏱️ Tempo Estimado: 35 minutos
📖 Cenário do Laboratório:

Implementar uma política de computação corporativa que force autotermination rígido de 20 minutos, proíba VMs de alto custo e configurar um Serverless SQL Warehouse com auto-stop de 1 minuto para o time de Analytics.

Tarefa 1 Criar uma Cluster Policy Restritiva em JSON

1. No workspace Databricks, vá em 'Compute' > aba 'Cluster policies' > 'Create policy'. 2. Nome da política: `DP750-Strict-FinOps`. 3. Cole o JSON de governança abaixo no editor:

Código para colar na célula do Notebook Databricks: 
{
  "autotermination_minutes": {
    "type": "range",
    "maxValue": 20,
    "defaultValue": 15,
    "isOptional": false
  },
  "node_type_id": {
    "type": "allowlist",
    "values": [
      "Standard_D4ds_v5",
      "Standard_D8ds_v5"
    ],
    "defaultValue": "Standard_D4ds_v5"
  },
  "custom_tags.CostCenter": {
    "type": "fixed",
    "value": "DataEngineering-DP750"
  }
}
✓ Saída Esperada no Console Databricks: ✓ Política DP750-Strict-FinOps criada com sucesso com limites rígidos de FinOps.

Tarefa 2 Conceder Permissão de Uso na Política

1. Na aba 'Permissions' da política recém-criada, adicione o grupo `users` com o privilégio `CAN_USE`. 2. Tente criar um cluster como usuário comum usando esta política e verifique que o autotermination não pode ultrapassar 20 minutos e instâncias com GPU estão bloqueadas.

Tarefa 3 Provisionar um Serverless SQL Warehouse

1. No menu lateral, alterne a persona para 'SQL' ou clique em 'SQL Warehouses'. 2. Clique em 'Create SQL Warehouse'. 3. Configure: - Name: `dp750-serverless-bi` - Cluster size: 2X-Small - Type: Serverless - Auto stop: 1 minute (desligamento ultrarrápido após inatividade) - Scaling: Min 1, Max 2 clusters. 4. Clique em 'Create' e execute uma query de teste no SQL Editor (`SELECT current_timestamp();`). 5. Verifique que o startup levou menos de 10 segundos!
