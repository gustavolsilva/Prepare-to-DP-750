🌐 Visão Unificada Completa: Integração Arquitetural de Ponta a Ponta

Processe fluxos contínuos de eventos com Spark Structured Streaming: garantias exactly-once via Checkpointing, controle de atraso com Watermarking e junções temporais stream-stream. Esta lição articula a ponte entre os fundamentos conceituais, a prática de engenharia no Azure Databricks e os critérios rigorosos de aprovação no exame Microsoft DP-750.

No dia a dia prático: O Spark Structured Streaming trata streams de dados como uma tabela append-only sem fim. Todo stream produtivo exige a definição de um `checkpointLocation` no ADLS Gen2 para armazenar o progresso do offset e o estado da query, garantindo tolerância a falhas e semântica exactly-once. Os modos de saída (`outputMode`) são: 'append' (novas linhas apenas), 'update' (linhas modificadas) e 'complete' (tabela de agregação inteira recalculada). Em agregações temporais (janelas tumbling ou sliding), o `withWatermark('event_time', '10 minutes')` define o limite máximo de atraso para descartar dados tardios e liberar memória RAM do State Store.

Diretriz oficial DP-750 & Decisão Arquitetural: Foco para o exame DP-750: O trigger `availableNow=True` combina o melhor dos dois mundos: ele processa todos os dados pendentes em micro-lotes com lógica de streaming incremental e desliga automaticamente o cluster ao terminar. Isso gera economias astronômicas de FinOps ao substituir clusters de streaming 24/7 por execuções acionadas a cada poucas horas. Em Stream-Stream Joins, o watermark é OBRIGATÓRIO em ambos os fluxos, acompanhado de uma restrição temporal na cláusula ON (ex: `b.time BETWEEN a.time AND a.time + INTERVAL 1 HOUR`).

Mecânica Interna & Governança Executiva: State Store Provider Internals: Por padrão, o Spark mantém o estado em memória JVM (HDFSBackedStateStoreProvider), que pode sofrer com Garbage Collection em streams de longa duração com milhões de chaves. A Databricks recomenda configurar RocksDB como State Store (`spark.sql.streaming.stateStore.providerClass = '...RocksDBStateStoreProvider'`), gravando o estado em disco local rápido de SSD e sincronizando assincronamente com o ADLS Gen2. Em termos de FinOps corporativo: SLA vs Custo: Nem todo pipeline precisa de latência de 2 segundos. O uso estratégico de triggers `availableNow` em conjunto com Job Clusters reduz o custo de infraestrutura em até 85% para fluxos com tolerância a dados semi-real time (ex: atualizações a cada 1 hora).

Lab 0012: Engenharia de Tempo Real com Structured Streaming e Watermarking

⏱️ Tempo Estimado: 35 minutos
📖 Cenário do Laboratório:

Processar um fluxo contínuo de cliques e telemetria, aplicando janelas temporais de agregação e descartando eventos com mais de 10 minutos de atraso para evitar esgotamento de memória no State Store.

Tarefa 1 Configurar Streaming com withWatermark e Janela Tumbling

1. Abra o notebook 'lab_0012_streaming_watermark'. 2. Execute a query de streaming em memória:

Código para colar na célula do Notebook Databricks: 
# COMMAND ----------
from pyspark.sql.functions import col, window, current_timestamp

# Gera stream sintético de eventos com timestamp
df_rate = spark.readStream.format("rate").option("rowsPerSecond", 5).load() \
               .withColumn("sensor_id", (col("value") % 3).cast("string")) \
               .withColumn("timestamp", current_timestamp())

# Define o Watermark de 10 minutos para descarte de dados atrasados
df_watermarked = df_rate.withWatermark("timestamp", "10 minutes") \
                        .groupBy(window("timestamp", "5 seconds"), "sensor_id") \
                        .count()

# Inicia o stream em memória para inspeção interativa
query = df_watermarked.writeStream \
                      .format("memory") \
                      .queryName("agregacao_sensores_stream") \
                      .outputMode("complete") \
                      .start()

query.awaitTermination(timeout=15)
query.stop()

# Consulta os resultados calculados pela janela
spark.sql("SELECT * FROM agregacao_sensores_stream ORDER BY window.start DESC LIMIT 10").show(truncate=False)

🎯 Desafio Flash DP-750

Um engenheiro de dados está projetando um pipeline em Structured Streaming que consome cliques de usuários de um Azure Event Hubs e agrega acessos por página em janelas de 15 minutos. Devido à instabilidade da rede celular dos usuários, alguns eventos chegam com até 20 minutos de atraso. Como evitar vazamento de memória (OutOfMemory) no cluster sem perder os eventos com atraso aceitável?
Definir withWatermark('click_time', '20 minutes') antes da agregação da janela temporal no DataFrame de streaming.
Aumentar a memória RAM do nó Driver para 512 GB e desabilitar o Garbage Collection.
Usar outputMode('complete') sem checkpointing configurado.
Mudar o pipeline para ler os dados exclusivamente em batch uma vez por mês.
