Control Plane vs Compute Plane, Driver & Executors, Catalyst Optimizer, Photon Engine C++, Pools e Governança de DBUs.

1. Control Plane vs Compute Plane no Azure Databricks

No Azure Databricks, a separação rígida de responsabilidades entre Control Plane e Compute Plane é a base de segurança, conformidade e governança de dados exigida no exame DP-750:

Camada Arquitetural Localização Física Componentes Hospedados Acesso a Dados de Clientes?
Control Plane Assinatura gerenciada pela Microsoft/Databricks na região do Azure Web Application UI, serviço de Notebooks, Job Scheduler, Cluster Manager e metadados de orquestração NUNCA (dados de negócio NUNCA residem nem transitam pelo Control Plane)
Compute Plane (Classic) Assinatura Azure do Cliente (Customer VNet gerenciada ou injetada) VMs dos Clusters (Driver e Workers), armazenamento DBFS raiz local e caches em memória/disco SIM (lê e grava diretamente nos containers do ADLS Gen2 via credenciais seguras)
Compute Plane (Serverless) Rede segura isolada gerenciada pela Databricks na mesma região do cliente MicroVMs efêmeras, Serverless SQL Warehouses, Serverless Jobs e pipelines de computação sob demanda SIM (acessa o ADLS Gen2 do cliente via túneis privados e credenciais efêmeras do Entra ID)

2. Conectividade Segura: Secure Cluster Connectivity & Private Link

  • Secure Cluster Connectivity (No Public IP - NPIP): Por padrão, os nós de computação no Compute Plane não possuem endereços IP públicos. Toda comunicação com o Control Plane ocorre via túneis TLS de saída (outbound) na porta 443 através de uma interface de rede segura (SCC relay). Não é necessário abrir nenhuma porta de entrada (inbound) no NSG.
  • VNet Injection: Permite implantar o Compute Plane em uma Rede Virtual (VNet) própria do cliente. Requisito do DP-750: Exige exatamente duas subnets dedicadas (uma pública/host e uma privada/container), cada uma com tamanho mínimo /26 (recomendado /24), delegadas exclusivamente para o serviço Microsoft.Databricks/workspaces.
  • Azure Private Link:
    • Front-end Private Link: Isola o acesso de analistas e conexões REST API do portal web, eliminando a exposição pública da UI do workspace.
    • Back-end Private Link: Isola a comunicação interna entre os nós do Compute Plane e a infraestrutura de gerenciamento do Control Plane.

3. Anatomia do Apache Spark & Pipeline do Catalyst Optimizer

O Apache Spark opera sob o modelo mestre-trabalhador (Master-Worker), onde o Driver coordena a execução e os Executors processam partições de dados:

-- Fluxo de Compilação de Consultas no Apache Spark:
1. Unresolved Logical Plan: Sintaxe inicial de DataFrames PySpark ou consultas Spark SQL.
2. Analyzed Logical Plan: Validação de nomes de tabelas, colunas e tipos contra o Unity Catalog Metastore.
3. Optimized Logical Plan: Aplicação de regras heurísticas do Catalyst:
   - Predicate Pushdown (empurra filtros para o storage ADLS Gen2 antes de ler tudo).
   - Column Pruning (elimina colunas desnecessárias da memória).
   - Constant Folding e simplificação de expressões booleanas.
4. Physical Plans: Geração de múltiplos planos físicos candidatos avaliados pelo Cost-Based Optimizer (CBO).
5. Selected Physical Plan: Compilação do plano vencedor para:
   - WholeStageCodegen (Bytecode Java otimizado via Tungsten).
   - Photon Execution Engine (Instruções C++ vetorizadas SIMD caso habilitado).

4. Photon Engine Vectorized Execution vs Spark Tradicional

Dimensão Apache Spark Tradicional (Tungsten) Photon Engine (C++ Vetorizado)
Linguagem do Motor Java / Scala compilado para bytecode na JVM C++ nativo com instruções de CPU vetorizadas (SIMD)
Processamento de Dados Iterador linha a linha com sobrecarga de chamadas de métodos Processa blocos de milhares de linhas por ciclo de clock de CPU
Impacto de Garbage Collection Sujeito a pausas de GC da JVM em grandes joins e agregações Gerenciamento nativo de memória fora da JVM (Zero pausas de GC)
Ganhos de Performance Linha de base Aceleração de 3x a 8x em scans Delta, agregações, joins e merges

5. Matriz de Tipos de Computação & FinOps de DBUs

Tipo de Cluster Caso de Uso Recomendado Custo de DBUs Política de Autotermination Recomendada
All-Purpose Cluster Desenvolvimento interativo, exploração de dados e testes em notebooks Alta (~$0.55/DBU) 15 a 20 minutos (imposto rigorosamente via Cluster Policy)
Job Cluster (Efêmero) Workloads de produção agendados via Databricks Workflows Baixa (~$0.20-0.40/DBU; até 60% mais barato) Destruído automaticamente logo após a conclusão da tarefa
Serverless SQL Warehouse Dashboards BI (Power BI), consultas analíticas ad-hoc e Lakeview Cobrança por segundo exato 1 a 5 minutos de inatividade (inicialização instantânea sub-10s)
Databricks Instance Pool Reduzir tempo de boot de clusters recorrentes de 5-7 min para < 30s Zero DBU enquanto ocioso (apenas custo de VM Azure) Configurar Min Idle instances durante horário comercial
Single-Node Cluster Cargas de trabalho que não precisam de paralelismo (MLflow, APIs, metadados) Baixíssima (1 única VM atuando como Driver e Executor) Desativa workers; previne alocação desnecessária de nós

6. ⚠️ Pegadinhas Críticas do Exame DP-750 (Arquitetura & FinOps)

  • All-Purpose vs Job Cluster em Produção: Se a questão mencionar um pipeline que roda diariamente ou periodicamente e perguntar como reduzir custos de nuvem, a resposta correta SEMPRE envolve migrar o notebook para um Databricks Workflow orquestrado com Job Cluster efêmero.
  • Montagens Legadas no DBFS (/mnt): O exame considera o uso de dbutils.fs.mount() e chaves de acesso em texto plano uma prática legada obsoleta. A abordagem moderna oficial do DP-750 exige Unity Catalog com Storage Credentials e External Locations ou Volumes.
  • Subnets para VNet Injection: Lembre-se: duas subnets exclusivas, tamanho mínimo /26, delegadas para Microsoft.Databricks/workspaces. Elas NÃO podem ser compartilhadas com nenhum outro recurso da Azure.
