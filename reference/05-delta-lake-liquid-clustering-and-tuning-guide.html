Folha 05: Guia de Otimização Física: Liquid Clustering & Tuning de Performance

Liquid Clustering (CLUSTER BY) vs Particionamento Hive, Deletion Vectors, OPTIMIZE, VACUUM e Diagnóstico na Spark UI.

1. Liquid Clustering (CLUSTER BY) vs Particionamento Tradicional Hive

O Liquid Clustering é a inovação mais importante de layout físico do Delta Lake no exame DP-750, substituindo o particionamento rígido Hive e o Z-Order tradicional:

Característica Particionamento Tradicional Hive (PARTITIONED BY) Liquid Clustering (CLUSTER BY) — Padrão DP-750
Flexibilidade de Colunas Rígido: alterar as colunas de partição exige recriar e reescrever a tabela Dinâmico: você pode alterar as chaves de clusterização com ALTER TABLE a qualquer momento
Problema de Small Files Severo: colunas com alta cardinalidade geram milhões de pequenos arquivos Inexistente: o algoritmo agrupa dados mantendo arquivos de tamanho ideal (~1 GB)
Custo de Manutenção O comando ZORDER exige reordenações globais caras e lentas O comando OPTIMIZE opera de forma incremental, clusterizando apenas novos dados
Concorrência de Escrita Conflitos frequentes em commits simultâneos na mesma partição Excelente concorrência, especialmente combinado com Deletion Vectors

2. Sintaxe Oficial de Liquid Clustering no SQL

-- Criação de tabela com Liquid Clustering por múltiplas colunas:
CREATE TABLE prod_lakehouse.gold.vendas_analiticas (
    id_pedido BIGINT,
    data_pedido DATE,
    id_cliente INT,
    codigo_pais STRING,
    valor_total DECIMAL(10,2)
)
CLUSTER BY (codigo_pais, data_pedido, id_cliente);

-- Alterando as colunas de clusterização sem reescrever a tabela:
ALTER TABLE prod_lakehouse.gold.vendas_analiticas
CLUSTER BY (codigo_pais, data_pedido);

-- Executando a otimização incremental:
OPTIMIZE prod_lakehouse.gold.vendas_analiticas;

3. Deletion Vectors (Mutações Ultrarrápidas no Delta Lake)

No Delta Lake tradicional, quando uma única linha era excluída ou atualizada em um arquivo Parquet de 100 MB, o Spark precisava reescrever o arquivo inteiro de 100 MB (Copy-on-Write). Com Deletion Vectors:

  • O Delta grava um arquivo leve de bitmap (vetor de bits) indicando apenas os números das linhas deletadas/atualizadas.
  • As consultas de leitura aplicam o bitmap em memória, ignorando as linhas removidas instantaneamente.
  • Reduz o tempo de MERGE INTO, DELETE e UPDATE em até 10x!
  • Habilitação: ALTER TABLE tbl SET TBLPROPERTIES ('delta.enableDeletionVectors' = true);

4. Comandos de Manutenção Física: OPTIMIZE e VACUUM

-- 1. OPTIMIZE: Bin-packing de pequenos arquivos para consolidar em arquivos de ~1 GB
OPTIMIZE prod_lakehouse.silver.fatos_transacoes;

-- 2. VACUUM: Limpeza de arquivos Parquet órfãos desassociados do log após transações
-- Remove apenas arquivos com mais de 7 dias (período de retenção padrão seguro)
VACUUM prod_lakehouse.silver.fatos_transacoes;

-- 3. VACUUM com retenção personalizada (ex: 3 dias / 72 horas para auditoria):
VACUUM prod_lakehouse.silver.fatos_transacoes RETAIN 72 HOURS;

5. Diagnóstico de Gargalos na Spark UI

Sintoma na Spark UI Causa Raiz Técnica Ação Corretiva Recomendada
Spill (Memory / Disk) Partições de Shuffle excedem a memória RAM alocada para os slots dos executors Aumentar spark.sql.shuffle.partitions ou migrar para nós de VM otimizados para memória
Data Skew (Stragglers) Poucas tasks demoram minutos enquanto 199 tasks concluem em 2 segundos Usar Skew Join Hint /*+ SKEW */ ou técnica de Salting na chave do Join
Garbage Collection Pauses Alta taxa de alocação de objetos temporários na JVM do Java Habilitar o Photon Engine para execução nativa C++ fora da JVM

6. ⚠️ Pegadinhas Críticas do Exame DP-750 (Delta Lake & Otimização)

  • O Perigo do VACUUM RETAIN 0 HOURS: Executar VACUUM tbl RETAIN 0 HOURS; falhará por padrão devido à trava de segurança spark.databricks.delta.retentionDurationCheck.enabled. Se forçada, essa ação DESTRÓI imediatamente a capacidade de Time Travel e corromperá leituras concorrentes em andamento!
  • Quando usar Liquid Clustering? Tabelas com padrões de consulta imprevisíveis, tabelas com cardinalidade variável ou tabelas atualizadas frequentemente com MERGE. O DP-750 prioriza Liquid Clustering em relação ao particionamento Hive.
